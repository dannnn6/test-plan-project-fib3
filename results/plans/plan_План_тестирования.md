## 2.1 Содержание документа

Документ определяет границы, ресурсы, стратегию, виды проверок, управление сборками и дефектами, критерии качества, риски, график и отчетность тестирования **полной версии** BookSphere. Содержит способы проверки клиентской веб- и мобильной части, административных функций, коммерческих процессов, микросервисов, хранилищ, внешних интеграций, нефункциональных характеристик и моделей монетизации.

## 2.5 Обзор программного продукта

BookSphere — масштабируемая Headless Commerce платформа продажи печатных, электронных и аудиокниг. Клиентские каналы, описанные как реализуемые: Web на Next.js с SSR/SSG и мобильное приложение Flutter для iOS/Android с аудиоплеером и офлайн-чтением. UI-технологии: Tailwind CSS, Framer Motion. Дальнейшие возможные каналы Headless (Smart TV, голосовые ассистенты) названы как адаптируемые каналы, но реализация клиентов и их срок не подтверждены.

Паспорт описывает контейнеризованные микросервисы: каталог и поиск — Python/FastAPI и Elasticsearch; корзина и заказы — Node.js/NestJS; пользователи и аутентификация — Go/Gin и Keycloak; AI-рекомендации — Python и **PyTorch либо TensorFlow**. Указаны PostgreSQL (операционные данные), Redis (кэш, сессии и корзины), MongoDB (отзывы, журналы действий), S3-совместимое объектное хранилище и DRM-сервер. Headless CMS: **Strapi либо Sanity**; API Gateway: **Kong либо AWS API Gateway**. Инфраструктурные варианты в паспорте: **Yandex Cloud / AWS / Kubernetes** (первые два — облачные платформы, Kubernetes — оркестратор; их перечисление не подтверждает совместного использования либо конкретной конфигурации); CI/CD: **GitLab CI либо GitHub Actions**. Наблюдаемость: Prometheus, Grafana, ELK Stack, Sentry. Перечисление альтернатив не означает выбор конкретного варианта; облачная платформа, набор сервисов и фактические версии подлежат подтверждению.

Основные возможности: расширенный поиск и каталог; карточка книги и отзывы; кабинет, библиотека, синхронизация, лояльность и вишлисты; персональные AI-рекомендации; гостевой checkout, доставка и оплата; PIM, OMS, маркетинг, BI; подписка, маркетплейс и B2B-лицензии; книжные клубы, голосовые отзывы, публичные полки, AR-витрина, эко-трекинг и Immersion Reading.

## 4.2 Тестовая конфигурация

**Предложение:** выделить логические назначения окружений `DEV` (поддержка разработки), `QA` (функциональные и регрессионные проверки), `STAGE` (интеграционные/E2E и приемочные проверки) и `LOAD` (изоляция нагрузочных и аварийных испытаний). Допустимо объединение окружений лишь при документированном контроле помех, данных и рисков; `PROD` не предназначена для разрушающих испытаний. Это схема назначений, а не утверждение о созданных стендах. Для проверок нагрузки и восстановления требуется **репрезентативная по топологии и лимитам** среда; фактические мощности, стоимости и расположение неизвестны. Применять лишь фактически выбранные варианты компонентов из альтернатив паспорта.

|---|---|---|
| Web | Next.js/React, SSR/SSG, Tailwind CSS, Framer Motion, браузеры разных движков; тестовое доменное имя и TLS | Поддерживаемые браузеры/версии, политики SEO и cookie |
| Mobile | Flutter iOS/Android, аудиоплеер, офлайн-ридер, камера для AR; реальные устройства/эмуляторы | Матрица ОС, моделей, минимальных версий, офлайн-объем |
| API и приложения | Контейнеры микросервисов, FastAPI, NestJS, Gin/Keycloak, AI runtime, API Gateway | Версии, контракты, выбранный Gateway, конфигурации |
| Данные/медиа | PostgreSQL, Redis, MongoDB, Elasticsearch, S3-совместимое хранилище, DRM-сервис | Версии, резервирование, ключи/шифрование, объемы |
| CMS/инфраструктура | Выбранная CMS (Strapi/Sanity), облако и оркестрация, конвейер GitLab CI/GitHub Actions | Фактический выбор платформы и сред |

Предусмотреть несколько пользователей и организаций, версионированную загрузку/очистку данных, синхронизированное время, эмуляцию плохой сети и отказов, безопасность тестовых секретов. Конкретные CPU/RAM, версии библиотек, масштаб кластера и допустимые сетевые задержки задаются по production-профилю; не фиксируются произвольно. Для сравнимости тестов сохранять снимок конфигурации/сборки и состояние тестового набора. **Обязательные измеряемые параметры среды до нагрузочных испытаний:** версии и число реплик сервисов, vCPU/RAM и лимиты контейнеров, конфигурация БД и индекса, объемы и распределение тестовых данных, кэш, сеть и задержки до зависимостей, конфигурация балансировщика, количество/мощность генераторов, время синхронизации часов, профиль запуска и наблюдаемость. Точные значения получить от архитекторов и эксплуатации; без них результаты нагрузки нельзя выдавать за соответствие промышленному контуру.

# 5 СТРАТЕГИЯ ТЕСТИРОВАНИЯ

Базовый подход — риско-ориентированное сочетание «черного ящика», контрактного и интеграционного тестирования, анализа технических метрик и выборочных проверок реализации. Уровни: модульные тесты разработчиков (наличие подтвердить), сервисные/API, интеграционные, E2E, системные, пользовательская приемка. Все обязательные пункты Full должны иметь трассировку, включая роли и нефункциональные требования.

## 5.1 Функциональное тестирование

Тест-дизайн: классы эквивалентности, граничные значения, таблицы решений для скидок/ролей/статусов, переходы состояний заказов, попарные комбинации форматов и каналов, сценарии конкуренции и восстановления после ошибок. В каждом модуле выполняются как успешные, так и отклоненные операции; для спорного результата требуется утвержденный ожидаемый результат.

### 5.1.1 Минимальный приемочный тест (Smoke test)

Для каждой сборки **предлагается** выполнять краткий smoke-набор: открытие Web/Mobile, доступность API и базового поиска, получение карточки, работа с тестовой корзиной, создание безопасного тестового заказа через sandbox, проверка библиотечного доступа тестового цифрового приобретения, входа внутренней роли и доступности PIM/OMS, базовые health checks микросервисов. При поврежденной интеграции, не входящей в smoke-набор, статус конкретного шага — `Blocked`, а решение о продолжении ограниченных проверок принимает QA-руководитель. Предлагаемый ориентир длительности smoke — **до одного часа при исправной тестовой среде**, не жесткое требование паспорта. **Предлагаемый критерий допуска:** каждый обязательный случай согласованного smoke-набора должен иметь `Pass`; `Fail`, `Blocked` и `Not Run` не удовлетворяют критерию. Если из-за сбоя невозможно запустить одну ветвь, QA-руководитель может разрешить проверку независимых модулей, но сборка не получает общий статус «smoke пройден». Состав обязательных случаев, их идентификаторы и границы независимости утверждаются до запуска.

### 5.1.2 Регрессионное тестирование

На каждом релевантном изменении запускать автоматизированный smoke и регрессионные тесты затронутых модулей; до релиза — полный согласованный регрессионный набор и E2E. Повторно проверять исправленные дефекты, соседние процессы и ранее успешные сценарии. Особый контроль: платежи и повторные уведомления, состояние корзины/остатков, права на контент, поиск после PIM-изменений, подписки, скидки, B2B-изоляция и совместимость Web/Mobile/API. Доля автоматизации и периодичность — по оценке рисков/ресурсов, **предложение**.

### 5.1.3 Функциональный тест

Проверять полные таблицы разрешений и статусов, валидации форм, ошибки данных и файлов, предельные значения по документированным ограничениям, пустые результаты, повторы операций, конкурентные изменения, конфликтующие обновления, прерывания связи, восстановление и идемпотентность. Параметры для тест-дизайна получают из контрактов: нельзя придумывать максимальное число бонусов, размер файла, длительность сессии или лимиты подписки. Проверять доступность ключевых задач на пользовательских устройствах и корректность международных/локальных условий только в подтвержденных регионах. Фактическая приемка каждой проверки — по ожидаемому результату утвержденного кейса.

## 5.2 Автоматизированное тестирование

**Предложение:** в CI запускать сервисные контрактные и API-проверки схем, ролей, ошибок, отрицательных ответов и идемпотентности; автоматизировать регрессионные пользовательские цепочки оформления заказа, публикации каталога, доступа к библиотеке, синхронизации, подписки и B2B; дополнить тестами преобразования CSV/XML, расчета скидок/комиссий по утвержденным правилам, синхронизации ERP, метриками BI на эталонном наборе. Тесты против реальных шлюзов — только в выделенных sandbox и с учетом ограничений; остальные негативные сценарии — на контролируемых заглушках. Хранить версии сценариев, фикстур и артефактов в репозитории, секреты — вне исходного кода. Выбор фреймворков и порог покрытия кода/автотестов согласовать; **никакой инструмент автоматизации не заявляется уже внедренным**.

## 5.3 Техническое тестирование

| Область | Метод и наблюдения | Критерий/неопределенность |

**Порядок SLA:** 99,9% за обычный 365-дневный год соответствует примерно **8 ч 45 мин 36 с** общей недоступности **только если** используется календарный год и весь простой учитывается одинаково. Лимит **8 часов планового простоя в год** — самостоятельное условие паспорта, не заменяющее SLA. Если плановые работы исключены из SLA, допустимый неплановый простой будет рассчитываться отдельно по утвержденной формуле; складывать или вычитать бюджеты без согласования запрещено.

# 6 МЕТОДОЛОГИЯ ТЕСТИРОВАНИЯ

## 6.1 Обзор процесса

1. Получить и версионировать паспорт, обозначить состав Full и источник каждого требования.
2. Проанализировать неясные бизнес-правила, роли, альтернативы стека/интеграций и нефункциональные условия; зарегистрировать открытые вопросы.
3. Составить и согласовать тестовую стратегию, трассировку, оценки ресурсов и календарные зависимости.
4. Спроектировать сценарии и тест-кейсы с точными ожидаемыми результатами, тестовые данные и нагрузочные профили; провести ревью.
5. Подготовить или обновить тестовый стенд, доступы, sandbox, данные и наблюдаемость; зафиксировать конфигурацию.
6. Получить идентифицируемую сборку, изменения, ограничения и инструкции развертывания/отката.
7. Развернуть сборку; выполнить минимальный приемочный тест (smoke) и документировать решение о полном либо ограниченном продолжении проверки.
8. Провести функциональные, ролевые, негативные, контрактные и интеграционные проверки; зарегистрировать дефекты с доказательствами.
9. Провести сквозные E2E и технические проверки по согласованным профилям, включая 10 000 пользователей, API, доступность, защиту и autoscaling.
10. Проверить доступную пользовательскую/техническую документацию; ее отсутствие учесть как зависимость, а не как выполненную проверку.
11. Сообщить о дефектах, передать их разработчикам; разработчики устраняют ошибки и выпускают идентифицируемую новую сборку.
12. Получить уведомление о новых/измененных функциях; при необходимости обновить реестр требований, случаи и тестовые данные.
13. Повторно проверить исправления, затронутые сценарии и выполнить регрессию; повторить цикл поставка → smoke → проверки до решения о завершении.
14. Для релиз-кандидата выполнить полный согласованный приемочный и регрессионный набор, проверить выходные критерии, подготовить журнал, протокол и реестр остаточных рисков.
15. Подготовить заключение QA и передать проект уполномоченному владельцу решения о выпуске; любое изменение границ либо условный выпуск оформить отдельным решением.

Это **предлагаемый** процесс. Этапы тестирования могут повторяться для каждой поставки. Не предполагается, что дефекты или рабочая инфраструктура уже существуют.

## 6.3 Доставка новых версий программного продукта

### 6.3.1 Процесс доставки

**Предлагаемый порядок:** команда разработки публикует неизменяемый идентификатор сборки (коммит/тег и образы), описание изменений, известные ограничения, миграции, перечень затронутых сервисов, флаги функций, совместимость API и инструкции deploy/rollback; DevOps доставляет сборку согласованным CI/CD или иным защищенным способом в тестовую среду. QA фиксирует время получения, версии, конфигурацию, состояние тестовых данных и результат smoke. Средство доставки (GitLab CI или GitHub Actions), доступы и ответственные **не выбраны**. Поставки не требуют FTP или иных механизмов из исторического шаблона.

### 6.3.2 Критерии приемки на тестирование

Сборка допускается к запланированному объему проверок при наличии: идентификатора и changelog; работоспособного развертывания; требуемых сервисов, тестовых учетных записей, данных и контрактов; работоспособных критичных smoke-сценариев; возможности регистрации результатов. При отсутствии изменений повторный прогон допускается, если он нужен для проверки среды или зависимостей. При падении критичного smoke, недоступном sandbox либо отсутствии данных испытания конкретной ветви отмечаются `Blocked`; тестирование других независимых ветвей может продолжаться по решению QA-руководителя. Блокирование не эквивалентно прохождению или отказу от обязательного функционального охвата.

## 6.4 Управление дефектами

**Предложение:** использовать общий дефект-трекер, выбранный проектом, с историей действий и ссылками на кейсы/сборки. Конкретная система **не определена**; ClearQuest из исходного шаблона не является требованием BookSphere. Дефект отделяется от предложения по улучшению и от вопроса к требованиям.

### 6.4.1 Определение степени важности дефектов

| Severity | Предлагаемое определение | Пример области последствий (не факт обнаружения) |
|---|---|---|
| Critical | Простой основной торговли, потеря данных, нарушение изоляции/прав, массовые неверные денежные операции или раскрытие защищенных данных. | Чужая цифровая библиотека, повторное списание, потеря заказа. |
| Major | Основной сценарий отдельного модуля недоступен или дает неверные результаты без безопасного обхода. | Некорректный остаток/стоимость доставки, отказ выдачи оплаченной книги. |
| Average | Частичный дефект с безопасным обходным путем без нарушения ключевой целостности. | Сбой отдельного фильтра при доступном альтернативном поиске. |
| Minor | Косметическое/некритичное отклонение без существенного влияния на сценарий. | Некорректный отступ или второстепенный текст. |

Уровень может быть повышен с учетом масштаба воздействия и нормативных последствий; примеры не означают наличие подобных ошибок в продукте.

### 6.4.2 Определение приоритета дефектов

| Priority | Предлагаемое значение |
|---|---|
| P0 — незамедлительно | Прекращение критичной эксплуатации/проверки; решение о блокировании релиза и срочном исправлении. |
| P1 — высокий | Исправление до релиза Full; высокий бизнес- или защитный риск. |
| P2 — обычный | Исправление в ближайшем согласованном цикле при отсутствии блокирующего влияния. |
| P3 — низкий | Согласованный бэклог с зафиксированным остаточным риском. |
| Enhancement | **Отдельный тип записи**, а не замена severity или обязательное требование. |

Приоритет определяется влиянием, частотой, возможностью обхода и сроком поставки; не равен severity. SLA реакции и исправления **не установлены**, их нельзя предполагать.

### 6.4.3 Цикл жизни дефекта

**Предлагаемая схема:** `Зарегистрирован (Submitted)` → `Открыт (Opened)` → `Исправлен, ожидает проверки (Resolved)` → `Закрыт (Closed)`; при неудачной проверке `Resolved` → `Opened`; повторное проявление `Closed` → `Opened`. Дополнительные терминальные/временные состояния `Дубликат (Duplicated)` и `Отложен (Postponed)` допускают возврат в обработку. Отклонение как не-дефекта допускается только с документированной причиной, ссылкой на требование и ответственным решением. Инструмент может использовать другие названия при сохранении смысловых переходов и аудита.

| Исходное состояние | Действие | Новое состояние | Кто инициирует / контроль |

| Нет | Создать запись | Submitted | QA; полнота полей |

| Opened | Отложить | Postponed | Уполномоченный владелец релизных рисков; причина |
| Opened | Передать на повторную проверку | Resolved | Разработчик; версия исправления |

Матрица — проект процесса, а не подтвержденные возможности трекера. Прямое удаление записи исключается из рекомендуемого процесса ради сохранения истории.

### 6.4.5 Процесс взаимодействия команд тестирования и разработки ПО при работе с дефект-трекинговой системой

QA регистрирует воспроизведение, ожидаемое/фактическое поведение и доказательства. Руководитель QA или назначенный специалист по первичному разбору дефектов проверяет полноту, риск и передает ответственному разработчику. Разработчик уточняет причины, указывает измененный компонент и точную сборку исправления. QA верифицирует исправление **на указанной сборке**, повторяет затронутую регрессию, закрывает либо возвращает дефект. При разногласии по требованиям владелец продукта/аналитик документирует решение; изменение требований проходит отдельное согласование. Дубликаты связываются с первичным тикетом, отложенные проблемы учитываются в отчете об остаточных рисках. Канал уведомлений и частота первичного разбора дефектов — согласовать.

### 6.4.6 Регистрация дефектов

| Поле | Содержание |

| Заголовок (Headline) | Однозначная краткая формулировка и модуль. |

| Сборка / окружение | Тег/коммит, версии сервиса, среда, браузер/ОС/устройство. |

### 6.4.7 Критерии качества продукта

**Предлагаемые измеримые критерии выхода и релизного решения** (подлежат утверждению; не являются фактическими результатами):

1. **Трассировка и полнота Full.** Предлагаемый критерий: 100% применимых требований паспорта (знаменатель — утвержденный реестр требований Full с уникальными ID) имеют минимум один утвержденный тест-кейс, а все существенные роли, интеграционные интерфейсы и сквозные цепочки представлены в матрице. Отдельно вывести числом и долей: требования с результатом `Pass`, `Fail`, `Blocked`, `Not Run`, с отсутствующим эталоном и с согласованным изменением границ. Ни `Blocked`, ни исключение не считаются успешной проверкой.
2. **Завершение исполнения.** **Предложение:** все обязательные приемочные случаи для утвержденного Full должны иметь именно итог `Pass` на релиз-кандидате. Показатели: `доля выполненных = (Pass + Fail) / число обязательных кейсов × 100%`, `доля успешных = Pass / число обязательных кейсов × 100%`, `доля исключений = исключенные / число исходно применимых кейсов × 100%`; отчет обязан показывать числители и знаменатели. До изменения границ любая обязательная проверка со статусом `Fail`, `Blocked` или `Not Run` не позволяет дать безусловное заключение о готовности Full. Исключение — отдельное решение владельца продукта **об изменении требований/границ или осознанном условном выпуске**, а не превращение его в `Pass`; в таком случае заключение должно явно указывать неполноту.
3. **Дефекты.** **Предложение:** перед безусловным допуском полной версии — 0 открытых дефектов с важностью `Critical` и 0 открытых `Major` во всех включенных в Full модулях, а не только в коммерческих сценариях. Для `Average`/`Minor` — зарегистрированное решение и оценка остаточного риска. Важность дефекта (`Severity`) не тождественна приоритету исправления (`Priority`); любые отступления требуют отдельного условного релизного решения.
4. **Финансы, целостность, права.** Для всех согласованных эталонных кейсов подтвердить точные суммы, статусы заказов/оплат, начисления, складские остатки, цифровые права и межорганизационную изоляцию; отсутствие утвержденного финансового алгоритма означает `Blocked`, а не `Pass`. Ожидаемые значения и допустимые погрешности (если применимы) утверждаются до исполнения.
5. **Время API менее 200 мс.** **Источник:** порог `< 200 мс` (строго меньше, а не меньше либо равно). **До измерений обязательно согласовать:** перечень методов/endpoint, точку отсчета и остановки таймера (серверная обработка либо end-to-end), статистику (например, p95 — **только предложение**, не заданный источником выбор), профиль нагрузки и одновременную активность, объем/состояние данных и кэша, размер запросов, сетевые условия, число прогонов, прогрев, интервал измерения и допустимую ошибочность. Условие `Pass` формулируется **после** согласования статистики как сравнение измеренного показателя для каждого обязательного API с 200 мс на согласованном профиле; публикуются первичные измерения и способ расчета. Пока критерий не определен, утверждать его выполнение нельзя.
6. **10 000 одновременных пользователей.** **Источник:** поддержка до 10 000 одновременно использующих систему пользователей на пике. **Уточнить:** учет уникальных авторизованных/гостевых сессий, определение «активен», доли потоков поиска, просмотра, чтения, оформления, паузы пользователя (`think time`), скорость выхода на пик, длительность устойчивого плато, допустимые отказы, целевую задержку и показатели исправности заказов. **Предложение:** в течение согласованного плато поддерживать 10 000 активных виртуальных пользователей и фиксировать действительную конкурентность, успешность сквозных действий, задержки и ресурсы; необходимый RPS/TPS **измерять отдельно**, не подставляя вместо числа пользователей. Границы допустимых ошибок должны быть утверждены до `Pass`.
7. **Доступность и плановые работы.** **Источник:** SLA 99,9% и отдельно не более 8 часов планового простоя в год. **Уточнить:** сервисную точку контроля, единицу инцидента, календарный период и часовой пояс, измерительный интервал, учет частичной деградации, правила исключения подтвержденных плановых окон из SLA, начало/окончание инцидента. **Предлагаемые самостоятельные расчеты после согласования:** `SLA = (учетное время − учитываемая недоступность) / учетное время × 100%`, проверка `SLA ≥ 99,9%`; `сумма длительностей плановых простоев за год ≤ 8 часов`. «Учетное время» и «учитываемая недоступность» определяются утвержденной политикой; нельзя автоматически складывать два бюджета или считать 8 часов частью разрешенного простоя по SLA. Краткие лабораторные испытания проверяют механизмы доступности и расчет, но **не доказывают годовой эксплуатационный SLA**.
8. **Защита и нормативные требования.** Предложение: обязательные утвержденные негативные сценарии доступа и утечки данных имеют `Pass`, нет открытых блокирующих уязвимостей в проверенном объеме. Отдельно провести оценку применимости PCI DSS, 152-ФЗ и GDPR и определить нужные независимые свидетельства соблюдения; QA не заменяет юридическую проверку или сертификацию.
9. **Завершение работ и решение о релизе.** Доступны журнал по каждой сборке, протоколы с эталонами, версиями и доказательствами, отчет о нагрузке, покрытие по ID требований, число и перечень непроверенных пунктов, реестр дефектов и остаточных рисков. QA составляет заключение **безусловно готов / условно готов с перечислением невыполненных критериев / не готов**, решение принимает назначенный владелец релиза. До назначения ответственного или закрытия обязательных вопросов безусловная приемка не подтверждается.

**Вопросы для согласования релизного допуска:** количественная доля допустимых некритичных неуспехов, точная severity/priority политика, критерии точности BI/AI, лимиты времени восстановления, тестовое покрытие клиентов, ошибки/частота логистических событий и ответственный за окончательное решение. Пока эти вопросы не закрыты, соответствие не может быть подтверждено в полном объеме.

### 6.4.8 Правила наименования пользователей системы CQ

Название раздела сохранено **дословно по исходному шаблону** ради структурной совместимости; CQ (ClearQuest) **не выбран и не требуется** паспортом. Поэтому конкретные правила именования учетных записей CQ **неприменимы**. **Предложение для выбранного трекера:** корпоративные уникальные идентификаторы пользователей с отображаемыми именами и ролью, недопущение общих учетных записей, аудит действий и назначение минимальных привилегий. Правила именования и SSO/процедура предоставления доступа утверждаются после выбора трекера. Не переносить историческую схему и персональные реквизиты из шаблона.

### 6.4.9 Правила ведения переписки

**Предложение:** официальные решения по требованиям, релизным рискам и исправлениям документировать в трекере с идентификатором задания; оперативные обсуждения — в согласованном канале. Обращение должно содержать тему/ID, компонент и сборку, вопрос, ожидаемое решение и срок, ответственного и приложенные обезличенные материалы. При блокировании платежей, данных или доступа — немедленно эскалировать руководителю QA и ответственному техническому руководителю; для остальных случаев применять согласованный регламент. **Срок ответа в часах, список контактных лиц и канал коммуникаций не установлены**; значения из прежнего шаблона не переносятся. Итоги устного решения фиксируются письменно.

# 7 ГРАФИК ТЕСТИРОВАНИЯ

## 7.1 Ссылка на проектный план

В паспорте BookSphere приведены ориентировочные **этапы разработки продукта**, а не утвержденные даты данного тест-проекта: Discovery и аналитика — 1–2 месяца; проектирование и дизайн — 2 месяца; MVP — 3–4 месяца; разработка Full — 3–4 месяца; QA и нагрузочное тестирование — 1 месяц; далее релиз и поддержка. Даты начала/окончания, зависимости, ресурсы, календарь и фактическое перекрытие этапов **не указаны**. План-график/ссылка на его файл **отсутствуют**. **Предложение:** получить актуальную дорожную карту и вести связанный график QA, не приравнивая упомянутый 1 месяц к гарантированной достаточности проверки полной версии.

## 7.2 Общая оценка временных затрат

Трудоемкость в человеко-днях **не рассчитана**, поскольку неизвестны завершенность реализации, численность и доступность команды, согласованные платформы, число интеграций, тестовые стенды, фактический объем регрессии и критерии нефункциональных проверок. Проставлять N/M/X/Y из шаблона или произвольные даты нельзя. **Метод предварительной оценки:** `Трудоемкость блока = подготовка требований/сценариев + разработка данных + настройка среды + число кейсов × норматив выполнения + поддержка автоматизации + ожидаемые повторы + оформление результатов + резерв риска`. Все слагаемые выражаются в человеко-днях, расчет отдельно по ответственным ролям и по блокам A–G; длительность по календарю определяется доступностью команды и зависимостями, а не суммой человеко-дней. **Вопрос:** согласовать нормативы, число случаев, коэффициенты повторов, резерв, состав и доступность сотрудников. До этого невозможно проверить достаточность одного месяца QA из паспорта.

| Предлагаемый блок | Зависимости | Результат/контрольная точка |
|---|---|---|
| A. Уточнение требований и границ | Решения о Full, альтернативных интеграциях, ролях, бизнес-правилах | Утвержденный реестр требований и рисков |
| B. Проектирование тестов и данных | A, контрактные спецификации | Матрица, тест-кейсы, наборы данных |
| C. Подготовка стенда и sandbox | Выбор стека, ресурсы и учетные данные поставщиков | Воспроизводимое окружение, доступность наблюдаемости |
| D. Циклы smoke, функций и интеграций | B, C и доступные сборки | Журнал, дефекты, трассировка |
| E. Нагрузка, защита, устойчивость | Репрезентативная среда, согласованные пороги и сценарии | Протокол измерений, оценка рисков |
| F. Исправления и регрессия | D/E и поставка исправленных сборок | Перепроверка и статус каждого критичного пункта |
| G. Приемка Full и отчетность | Результаты D–F | Итоговый отчет и решение о допуске |

Фазы B/C могут идти параллельно, D–F повторяются; E не должен проходить на неподходящем малом стенде с выводами о production. После согласования входных данных QA lead оценивает по блокам объем тест-кейсов, трудозатраты, резерв на повторные циклы и критический путь; заказчик утверждает календарь. Ограничение «1 месяц QA» из паспорта следует трактовать как предварительный этап roadmap, а не обещание выполнить весь план за месяц независимо от ресурсов.

# 8 ОЦЕНКА РИСКОВ ПРОЕКТА ТЕСТИРОВАНИЯ

Ниже указаны **качественные экспертные предположения**, а не измеренная статистика. **Предлагаемая шкала вероятности:** низкая — возможна при отдельных специальных условиях, средняя — правдоподобна при обычном ходе проекта, высокая — ожидаема при сохранении уже известных зависимостей и неопределенностей; это не числовые вероятности. **Шкала влияния:** среднее — локальная задержка или дополнительная работа, высокое — срыв значимого этапа или приемки части Full, критическое — блокирование выпуска, существенная финансовая/правовая потеря или компрометация данных. Приоритет рассмотрения риска назначается по сочетанию вероятности и влияния с обязательным поднятием критического влияния на управленческий контроль. Оценки требуют подтверждения владельцами после обследования проекта.

| Риск | Предварительная вероятность / влияние | Владелец функции | План предупреждения/реагирования |
|---|---|---|---|
| Неопределенные бизнес-правила, роли и состав Full | Высокая / Высокое | Владелец продукта, аналитик | Реестр вопросов, утверждение контрактов и матрицы полномочий до приемочных кейсов |
| Сложность нескольких альтернативных интеграций и отсутствие sandbox | Высокая / Высокое | Интеграционный техлид, заказчик | Реестр фактически подключаемых поставщиков, договоренности о sandbox, mocks, статусы непокрытого |
| Неполная спецификация латентности и concurrency | Высокая / Высокое | Архитектор, QA performance | Формализовать p95/другую статистику, профиль активных сессий, данные, сеть, ошибки; калибровать генераторы |
| Разночтение SLA 99,9% и годового планового простоя | Высокая / Высокое | Владелец SLA/SRE | Утвердить формулу учета, точки измерения, календарь, исключения и отдельный учет плановых работ |
| Несоответствие тестовой среды production | Средняя / Высокое | Инженеры инфраструктуры и надежности (DevOps/SRE) | Профили конфигурации, контролируемая нагрузка, отчет об ограничении экстраполяции |
| Ошибка денежных операций, двойные webhooks и несогласованные остатки | Средняя / Критическое | Техлиды checkout/OMS | Идемпотентность, конкурентные E2E, сверка транзакций, sandbox сценарии отказа |
| Компрометация ПДн, цифрового контента, B2B-изоляции | Средняя / Критическое | Security/техлид IAM/DRM | Проверки авторизации, негативные API-тесты, закрытые медиа/секреты и профильный аудит |
| Некорректные AI/BI показатели, отсутствие эталонов | Высокая / Высокое | Data/BI lead, бизнес-владелец | Эталонные датасеты, формулы, сценарии холодного старта, договоренность о метриках |
| Блокирующая сборка и запоздалые исправления | Средняя / Высокое | Разработка, QA lead | Smoke-гейт, ранняя интеграция, повторные циклы, буфер в графике |
| Отставание графика при недостаточной QA-команде | Высокая / Высокое | Руководитель проекта | Оценить трудоемкость Full, параллелизм, критический путь; согласовать состав и сроки |
| Изменения требований на поздних этапах | Средняя / Высокое | Заказчик / продукт | Версионирование требований, impact analysis, ревью покрытия |
| Недостаточная координация команд и поставщиков | Средняя / Среднее | Руководители команд | Ответственные, triage, единый журнал вопросов, эскалация |
| Ошибки, проявившиеся после приемки | Средняя / Высокое | QA lead / владелец релиза | Риско-ориентированная регрессия, мониторинг, soft launch и фиксация остаточных рисков |
| Реальные экологические обещания/AR не имеют тестируемого контракта | Высокая / Среднее | Продукт, партнерские интеграции | Уточнить источник расчета, подтверждение компенсации, поддерживаемые устройства и ответственность партнера |

# 9 ОТЧЕТЫ О РЕЗУЛЬТАТАХ ТЕСТИРОВАНИЯ

**Предложение:** краткие отчеты о ходе QA на согласованной периодичности (ориентир — еженедельно и после значимых сборок), отдельно — заключение по релиз-кандидату. Отчетность фиксирует фактические запуски, а не предполагаемые успехи. Получателей и расписание согласовать.

## 9.1 Журнал тестирования

Вести журнал по каждому прогону, включая идентификатор версии, окружение, исполнителя, дату/время, компонент, функцию, ID сценария/кейса, тип теста, статус `Pass / Fail / Blocked / Not Run`, ссылку на доказательства и дефекты, причину блокирования. Для технических тестов — профиль нагрузки, число **одновременных пользователей**, наблюдаемые RPS/TPS, задержки, ошибки, ресурсы и версия конфигурации.

| Сборка | Компонент | Функция / кейс | Тип | Окружение | Результат | Дефект / доказательства |
|---|---|---|---|---|---|---|
| *Будет заполнено при выполнении* | — | — | — | — | — | — |

Строка выше — **пустой шаблон**, не запуск и не результат теста. В сводке отдельно считать запланированные, выполненные, успешные, неуспешные и заблокированные проверки; приводить долю покрытия с явным знаменателем и перечень непроверенных требований.

## 9.2 Протокол тестирования

Для каждого существенного прогона сохранять полный воспроизводимый протокол: ID требования/кейса; цель, предусловия и синтетические данные; точные шаги; ожидаемые результаты; наблюдения/артефакты; сборку и среду; время, автора и статус; ссылку на дефект. Для E2E — идентификаторы цепочки заказа/платежа/события, подтверждение сохраненного состояния систем и сопоставление с внешними sandbox. Для нагрузки — дату, топологию, профиль пользователей/переходов, прогрев, интервал измерения, percentiles, ошибки и ограничения среды. Формальные юридические акты аудита хранят отдельно от QA-протоколов.

**Предлагаемый пустой формат записи:** `TC-ID | REQ-ID | Build | Env | Preconditions | Test data | Steps | Expected | Actual | Status | Evidence | Defect-ID | Executor | Timestamp`. По состоянию на дату подготовки плана заполненных протоколов нет.

## 9.3 Отчет о зарегистрированных дефектах

Отчет формируется из выбранного трекера на дату среза (автоматическим экспортом при возможности). Поля: `ID | State | Module | Headline | Description | Owner | Severity | Priority | Found in | Fixed in | Requirement | Reproduction | Decision / Risk`. Сводка показывает число открытых проблем по severity/priority, время нахождения в статусах (после накопления данных), дефекты, блокирующие E2E или критерии Full, и согласованные отложенные решения. Реестр вопросов к требованиям и предложений по улучшению указывается отдельно, чтобы они не искажали счетчик дефектов.

В предоставленных исходных материалах **нет свидетельств выполненных проверок, зарегистрированных дефектов и согласованной приемки**; настоящий план не заявляет о проведении испытаний. Итоговый отчет должен отличать подтвержденное качество проверенной сборки от областей без наблюдений и содержать рекомендацию QA, решение владельца релиза и все принятые остаточные риски.
