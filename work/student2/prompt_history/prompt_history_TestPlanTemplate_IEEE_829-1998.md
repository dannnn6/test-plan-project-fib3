## 6. Подход к тестированию (Approach)

### 6.1. Общая стратегия

**[П]** Предлагается риск-ориентированный подход, сочетающий ручное, автоматизированное, интеграционное, системное и нефункциональное тестирование.

Тестирование организуется на следующих уровнях:

| Уровень | Цель |
|---|---|
| Компонентное | Проверка отдельных функций и компонентов |
| Интеграционное | Проверка взаимодействия микросервисов, БД и внешних систем |
| Системное | Проверка полной платформы в единой среде |
| Сквозное (E2E) | Проверка пользовательских процессов от начала до конечного результата |
| Регрессионное | Проверка ранее работавших возможностей после изменений |
| Приёмочное | Подтверждение соответствия согласованным требованиям |

### 6.7. Тестирование производительности

**[И]** Целевые требования паспорта:

|---|---|
| Набор API | Все методы или определённые критические endpoint |
| Точка измерения | Gateway, backend или внешний клиент |
| Метрика | Среднее, медиана, p95, p99 или абсолютное максимальное значение |
| Нагрузка | Количество одновременных пользователей и профиль запросов |
| Данные | Объём каталога, заказов и пользовательских записей |
| Кэш | Холодный, прогретый или смешанный режим |

Применять к порогу 200 мс конкретный процентиль можно только после его согласования. Сам паспорт этого не устанавливает.

#### 6.7.2. Одновременные пользователи

10 000 одновременных пользователей не эквивалентны 10 000 запросам в секунду.

Интенсивность запросов зависит от пользовательского поведения, интервалов ожидания, количества действий и длительности сессии.

**[П]** Предлагается нагрузочная модель с разными сценариями: просмотр каталога, поиск, карточки, корзина, оформление заказа, чтение, прослушивание и административные операции.

Следует измерять:

- количество активных пользователей;
- интенсивность запросов в секунду как отдельную метрику;
- задержки API;
- процент ошибок;
- загрузку CPU и RAM;
- обращения к БД;
- очереди и пулы соединений;
- эффективность кэширования;
- время масштабирования.

**[В]** Необходимо согласовать определение одновременного пользователя: авторизованная сессия, активный виртуальный пользователь, открытое соединение или пользователь, выполняющий действия в заданном временном окне.

### 6.8. Доступность и SLA

**[И]** Целевой SLA — 99,9%. В паспорте также указано ограничение планового простоя не более 8 часов в год.

Эти положения необходимо учитывать отдельно.

При расчётном периоде 365 суток общая продолжительность года составляет 8760 часов.

Если доступность 99,9% рассчитывается по полному календарному времени без исключений, максимально допустимый суммарный простой составляет:

8760 × 0,001 = **8,76 часа**, то есть 8 часов 45 минут 36 секунд.

Однако паспорт не определяет, включается ли плановый простой в расчёт SLA.

**[В]** Необходимо согласовать:

- учитывается ли плановый простой в показателе 99,9%;
- как определяется плановый и внеплановый простой;
- исключаются ли согласованные технологические окна из знаменателя;
- что считается недоступностью: весь сервис или отдельная критическая функция;
- как учитывается частичная деградация;
- какой календарный период используется;
- откуда берутся данные измерений;
- как учитываются сбои внешних провайдеров.

**[П]** До согласования методики следует независимо фиксировать:

1. Фактическую доступность сервиса.
2. Продолжительность плановых остановок.
3. Продолжительность внеплановых остановок.
4. Продолжительность частичной деградации.

Простой в течение ограниченного тестового периода не подтверждает сам по себе выполнение годового SLA.

- количество выполненных тестов;
- долю Passed, Failed, Blocked, Not Run;
- покрытие требований;
- количество дефектов по критичности;
- долю повторно открытых дефектов;
- длительность тестовых циклов;
- количество нестабильных автоматизированных тестов;
- производительность API;
- долю ошибочных запросов;
- результаты нагрузочного тестирования;
- показатели доступности;
- результаты проверок безопасности.

Фактические значения метрик появятся только после выполнения испытаний.

### 6.16. Управление конфигурациями и изменениями

Каждый тестовый прогон должен быть связан с конкретной сборкой, средой и набором данных.

При изменении требования необходимо:

1. Зарегистрировать изменение.
2. Оценить затронутые функции.
3. Обновить тестовые сценарии.
4. Пересмотреть риски.
5. Скорректировать сроки и ресурсы.
6. Выполнить необходимую регрессию.

Неясные или непроверяемые требования передаются на уточнение владельцу требований. До согласования ожидаемого поведения их нельзя считать объективно проверенными.

## 7. Критерии прохождения и непрохождения (Item Pass/Fail Criteria)

### 7.1. Критерии отдельного теста

Тест получает статус:

- **Passed** — фактический результат соответствует утверждённому ожидаемому.
- **Failed** — обнаружено отклонение от ожидаемого результата.
- **Blocked** — тест нельзя выполнить из-за препятствия.
- **Not Run** — тест не запускался.

**[П]** Дополнительно допускается статус Not Applicable для тестов, официально исключённых по утверждённому изменению состава релиза.

Тест считается пройденным только при наличии достаточных свидетельств выполнения.

### 7.2. Критерии функционального модуля

**[П]** Предлагаемые критерии:

1. Все обязательные требования модуля связаны с тестами.
2. Выполнены все критические сценарии.
3. Критические сценарии завершились успешно.
4. Все выявленные блокирующие и критические дефекты устранены.
5. Непрохождение остальных проверок отражено в отчёте.
6. Невыполненные сценарии и остаточные риски явно перечислены.
7. Результаты регрессии зарегистрированы.

### 7.3. Критерии завершения системного тестирования

**[П]** Предлагаемые пороги для согласования:

| Критерий | Предлагаемое значение |
|---|---|
| Покрытие утверждённых требований тестами | 100% |
| Выполнение обязательных тестов | 100% |
| Успешность критических E2E-сценариев | 100% |
| Открытые блокирующие дефекты | 0 |
| Открытые критические дефекты | 0 |
| Успешность всех выполненных обязательных тестов | Не менее 98% |
| Подтверждение нефункциональных требований | По согласованным методикам и порогам |
| Непроверенные обязательные требования | 0 без документально утверждённого исключения |
| Отчётность | Сформирован итоговый отчёт с результатами и остаточными рисками |

Порог 98% является предложением, а не требованием паспорта.

При его использовании все неуспешные тесты должны быть проанализированы; процент успешности не заменяет решения по рискам.

### 7.4. Критерии нефункциональных испытаний

| Требование | Критерий |
|---|---|
| API менее 200 мс | Выполнение согласованной метрики при согласованной нагрузке |
| 10 000 одновременных пользователей | Подтверждённая работа при согласованной модели пользовательской активности |
| SLA 99,9% | Соответствие утверждённой методике расчёта доступности |
| Плановый простой не более 8 ч/год | Соответствие отдельному годовому ограничению и правилам учёта |
| Auto-scaling | Корректное масштабирование при согласованных условиях |
| Безопасность | Отсутствие неприемлемых уязвимостей и выполнение согласованных проверок |
| Защита цифрового контента | Соблюдение утверждённых правил доступа и DRM |

**[В]** Пока методики не утверждены, соответствующие нефункциональные требования нельзя окончательно признать выполненными.

### 7.5. Решение о готовности

**[П]** Для выпуска предлагаются следующие категории решения:

- **Go** — согласованные критерии выполнены.
- **Conditional Go** — есть документально принятые остаточные риски, не нарушающие обязательные критерии.
- **No-Go** — обязательные критерии не выполнены.

Утверждать выпуск только на основании доли успешно пройденных тестов не рекомендуется.

## 8. Критерии приостановки и возобновления (Suspension Criteria and Resumption Requirements)

### 8.1. Основания приостановки

**[П]** Тестирование отдельного модуля или цикла приостанавливается, если:

1. Система недоступна и выполнение тестов невозможно.
2. Обнаружен блокирующий дефект, нарушающий основной бизнес-процесс.
3. Есть риск неконтролируемого повреждения данных.
4. Нарушена корректность или изоляция тестовой среды.
5. Не работают необходимые внешние интеграции и отсутствует пригодный имитатор.
6. Сборка не соответствует заявленной конфигурации.
7. Обнаружена критическая уязвимость, делающая дальнейшее использование среды небезопасным.
8. Невозможно достоверно определить ожидаемый результат.
9. Нагрузочное испытание создаёт недопустимый риск для используемой инфраструктуры.

Приостановка может касаться только затронутого набора тестов, если остальные проверки сохраняют смысл.

### 8.2. Условия возобновления

Для возобновления необходимо:

- устранить блокирующую причину;
- подтвердить работоспособность среды;
- зафиксировать новую конфигурацию при её изменении;
- восстановить требуемые тестовые данные;
- провести повторную проверку исправления;
- выполнить необходимую регрессию;
- задокументировать решение о продолжении.

### 8.3. Учёт прерванных тестов

Прерванные проверки должны получать статус Blocked, а не Failed, если несоответствие самого продукта не установлено.

После восстановления среды выполняются прерванные проверки и необходимые зависимые сценарии.

## 5. Функции, не подлежащие тестированию (Features Not To Be Tested)

### 5.1. Принцип исключения

Объём функциональных проверок определяется составом Full Version и утверждёнными требованиями.

Наличие в паспорте потенциального канала продаж не означает существование готового самостоятельного приложения для этого канала.

Отсутствие детального описания функции не считается самостоятельным основанием для её исключения, если функция входит в согласованный состав релиза.

### 5.2. Предварительные исключения

| Область | Статус | Обоснование |
|---|---|---|
| Самостоятельное Smart TV-приложение | Исключено из текущего функционального охвата | Потенциальный канал, отдельные требования отсутствуют |
| Самостоятельный голосовой ассистент | Исключён | Отдельные пользовательские сценарии не описаны |
| Иные будущие каналы продаж | Исключены | Не определён состав конкретных клиентов |
| Внутренний код платёжных провайдеров | Не тестируется | Внешнее ПО |
| Внутренний код служб доставки | Не тестируется | Проверяется интеграция |
| Внутренний код ERP и CRM | Не тестируется | Проверяется обмен с BookSphere |
| Внутреннее устройство сторонних фреймворков | Не тестируется отдельно | Проверяется использование в продукте |
| Несогласованные производственные операции с реальными платежами | Исключены из обычного тестового контура | Требуют специальных разрешений и условий |

### 5.3. Headless Commerce

**[И]** Архитектура Headless Commerce предусматривает возможность адаптации к разным каналам продаж.

Исключение отдельных Smart TV- и голосовых клиентов не исключает проверки серверного API, корректности его контрактов и возможности использования несколькими поддерживаемыми клиентами.

## 6. Подход к тестированию (Approach)

### 6.1. Стратегия

**[П]** Предлагается риск-ориентированная стратегия, сочетающая ручное и автоматизированное тестирование.

| Уровень | Назначение |
|---|---|
| Компонентное | Проверка отдельных программных компонентов |
| Интеграционное | Проверка контрактов и обмена между системами |
| Системное | Проверка полной платформы |
| Сквозное | Проверка целостных пользовательских процессов |
| Регрессионное | Выявление нарушений после изменений |
| Приёмочное | Подтверждение согласованных бизнес-требований |
| Нефункциональное | Оценка производительности, безопасности, устойчивости и совместимости |

Работы могут выполняться параллельно при готовности соответствующих компонентов.

### 6.2. Методы проектирования тестов

**[П]** Используются:

- классы эквивалентности;
- анализ граничных значений;
- таблицы принятия решений;
- переходы состояний;
- сценарное тестирование;
- попарное тестирование конфигураций;
- исследовательское тестирование;
- контрактное тестирование;
- тестирование на основе рисков.

Применение:

- цены, рейтинги, годы — границы;
- скидки и бонусы — таблицы решений;
- платежи, заказы, подписки — переходы состояний;
- роли — матрица доступа;
- устройства и браузеры — матрица совместимости;
- интеграции — контракты и обработка отказов.

### 6.3. Терминология проверок

Для единообразия документа используются следующие понятия:

- **Группа проверок** — набор испытаний определённой функции.
- **Тестовый сценарий** — описание проверяемой ситуации или последовательности действий.
- **Тест-кейс** — формализованная проверка с условиями, действиями и ожидаемым результатом.
- **Тестовый прогон** — выполнение набора тест-кейсов на определённой сборке.
- **Дефект** — установленное отклонение от утверждённого ожидаемого поведения.
- **Блокировка** — препятствие, не позволяющее выполнить тест или достоверно оценить результат.

Для цифрового контента используются термины:

- печатная книга;
- электронная книга;
- аудиокнига;
- цифровой контент — обобщающее понятие для электронных книг, аудиокниг и связанных цифровых материалов.

### 6.4. Матрица ролей

**[И]** Паспорт выделяет B2C-покупателей, B2B-клиентов, контент-менеджеров, маркетологов, операторов колл-центра и сотрудников склада.

Также предусмотрены гостевой checkout и сторонние продавцы маркетплейса.

### 6.5. Позитивные, негативные и граничные проверки

Для каждой функции должны проектироваться применимые проверки:

**Позитивные:**
- корректные данные;
- разрешённые действия;
- штатный бизнес-процесс;
- успешная интеграция.

**Негативные:**
- некорректные данные;
- отсутствие прав;
- недоступность зависимостей;
- неуспешный ответ;
- истечение срока операции;

**Граничные:**
- минимальные значения;
- максимальные значения;
- значения непосредственно за пределами диапазона;
- пустые наборы;
- большие наборы;
- граничные даты и сроки.

**[В]** Фактические ограничения должны определяться утверждёнными требованиями, а не произвольными значениями тестировщика.

### 6.12. SLA и простой

**[И]** Требования:

- доступность 99,9%;
- плановые работы — не более 8 часов простоя в год.

Для года продолжительностью 365 суток полное календарное время составляет 8760 часов.

При расчёте доступности по полному времени:

`8760 × (1 − 0,999) = 8,76 часа`.

Это 8 часов 45 минут 36 секунд.

Указанный расчёт не устанавливает порядок учёта плановых работ.

**[В]** Необходимо определить:

- учитываются ли плановые работы в SLA;
- какие операции считаются недоступностью;
- учитывается ли частичная деградация;
- какие компоненты входят в измеряемую услугу;
- какой временной период применяется;
- какие данные считаются официальным источником;
- как классифицируются сбои внешних провайдеров;
- какие плановые окна допустимы;
- как фиксируется начало и конец простоя.

**[П]** Рекомендуется независимо учитывать:

1. Общий простой.
2. Плановый простой.
3. Внеплановый простой.
4. Частичную деградацию.
5. Фактическую доступность по утверждённой формуле.

**Критерии прохождения:**

- SLA — соответствие утверждённой формуле доступности;
- плановый простой — не более 8 часов в год по утверждённым правилам учёта.

Краткосрочное испытание отказоустойчивости не подтверждает выполнение годового SLA. Для такого подтверждения необходим мониторинг за установленный период.

- применимость и объём требований 152-ФЗ;
- применимость GDPR;
- категории персональных данных;
- роли участников обработки данных;
- границы аудита;
- критерии допустимости уязвимостей.

DDoS-испытания проводятся только в разрешённой контролируемой среде с согласованными ограничениями.

### 6.16. Совместимость и интерфейсы

**[И]** Предусмотрены Web, iOS и Android.

**[П]** Рекомендуются проверки:

- поддерживаемых настольных браузеров;
- мобильных браузеров;
- Android и iOS;
- различных экранов;
- сенсорного управления;

- фонового режима;
- воспроизведения аудио;
- офлайн-чтения;
- восстановления работы.

Для Web дополнительно:

- серверная генерация страниц;
- статическая генерация;
- корректность метаданных;
- доступность содержимого для индексирования;
- обновление контента;
- отсутствие несоответствий между серверным и клиентским отображением.

**[В]** Требуется утвердить поддерживаемые ОС, браузеры, устройства, разрешения и SEO-критерии.

Проверки доступности интерфейса по конкретному стандарту могут быть предложены дополнительно, но паспорт такого стандарта не устанавливает.

**[П]** Предлагается автоматизировать:

- API-контракты;
- расчёт цен и скидок;
- переходы состояний;
- проверки авторизации;
- критические интеграции;
- основные E2E-сценарии;
- регрессию;
- нагрузочные испытания.

Возможные инструменты:

- Playwright — Web;
- Appium — Mobile;
- pytest и другие средства — API;
- k6 или JMeter — нагрузка;
- средства CI/CD выбранного проекта — запуск;
- Allure и аналогичные решения — отчётность.

Критерии выбора: совместимость, поддержка стека, стоимость сопровождения, воспроизводимость, опыт команды и возможность интеграции с CI/CD.

### 6.19. Регрессия

Регрессионные проверки выполняются после:

- исправления дефектов;
- изменения API;
- изменения схем данных;
- обновления зависимостей;
- изменения бизнес-правил;
- изменения конфигурации;
- подготовки релиз-кандидата.

Объём определяется затронутыми функциями и риском.

Для платежей, заказов, цифровых прав, авторизации и критических интеграций рекомендуется сохранять полный набор соответствующих критических регрессионных сценариев.

### 6.20. Метрики тестирования

| Метрика | Метод расчёта или учёта |
|---|---|
| Выполненные тесты | Количество тестов со статусом Passed или Failed |
| Passed | Количество успешно выполненных тестов |
| Failed | Количество тестов с установленным несоответствием |
| Blocked | Количество тестов, выполнение которых заблокировано |
| Not Run | Количество незапущенных тестов |
| Успешность выполнения | Passed / (Passed + Failed) × 100% |
| Покрытие требований | Количество требований с достаточным согласованным тестовым покрытием / количество применимых требований × 100% |
| Открытые дефекты | Количество незакрытых зарегистрированных дефектов |
| Повторно открытые дефекты | Количество дефектов, повторно открытых после исправления |
| Время ответа API | По утверждённой точке измерения и статистике |
| Интенсивность запросов | Успешные и неуспешные запросы за единицу времени |
| Доступность | По утверждённой методике SLA |

Метрики необходимо фиксировать по тестовому циклу, сборке, модулю и критичности проверок, где это применимо.

Показатель успешности не учитывает Blocked и Not Run в знаменателе, поэтому всегда должен рассматриваться совместно с показателями полноты выполнения.

### 6.21. Управление изменениями

При изменении требования:

1. Регистрируется изменение.
2. Определяются затронутые компоненты.
3. Пересматриваются тесты.
4. Обновляется матрица покрытия.
5. Пересматриваются риски.
6. Оценивается влияние на график.
7. Выполняется необходимая регрессия.

Непроверяемое требование направляется на уточнение.

Если ожидаемый результат не установлен, тест не может получить достоверный статус Passed по соответствующему требованию.

## 7. Критерии прохождения и непрохождения (Item Pass/Fail Criteria)

### 7.1. Статусы тестов

| Статус | Значение |
|---|---|
| Passed | Фактический результат соответствует утверждённому ожидаемому |
| Failed | Установлено отклонение |
| Blocked | Проверка не может быть выполнена или объективно оценена |
| Not Run | Проверка не выполнялась |
| Not Applicable | Проверка официально признана неприменимой |

Статус Not Applicable допускается только при документально подтверждённом основании.

### 7.2. Критерий отдельного тест-кейса

Тест считается пройденным, если:

1. Выполнены необходимые предусловия.
2. Использована зарегистрированная конфигурация.
3. Выполнены предусмотренные действия.
4. Фактический результат соответствует утверждённому ожидаемому.
5. Сохранены необходимые свидетельства.

Если ожидаемое поведение неизвестно, результат не должен объявляться успешным.

### 7.3. Критерии завершения функционального модуля

**[П]** Предлагается считать модуль готовым к завершению тестирования, если:

- все применимые утверждённые требования имеют достаточное тестовое покрытие;
- выполнены все обязательные проверки;
- критические сценарии имеют статус Passed;
- отсутствуют открытые блокирующие и критические дефекты;
- нет заблокированных обязательных проверок без утверждённого решения;
- выполнена необходимая регрессия;
- оформлены результаты и остаточные риски.

Достаточное покрытие подразумевает проверку соответствующих позитивных, негативных, граничных и интеграционных сценариев, а не просто наличие одного теста на требование.

### 7.4. Критерии завершения системного тестирования

**[П]** Предлагаемые значения для согласования:

| Критерий | Предложение |
|---|---|
| Покрытие применимых утверждённых требований | 100% |
| Выполнение обязательных тестов | 100% |
| Passed среди критических E2E-сценариев | 100% |
| Открытые блокирующие дефекты | 0 |
| Открытые критические дефекты | 0 |
| Blocked среди обязательных проверок | 0 без утверждённого исключения или решения |
| Not Run среди обязательных проверок | 0 без утверждённого исключения |
| Успешность всех выполненных тестов | Не менее 98%, предлагаемый дополнительный показатель |
| Нефункциональные требования | Подтверждены согласно согласованным методикам |
| Итоговая отчётность | Подготовлена |

Порог 98% не является требованием паспорта.

Он не заменяет условия выполнения обязательных и критических тестов.

Если обязательная проверка завершилась Failed, общая доля Passed сама по себе не подтверждает готовность продукта.

### 7.5. Нефункциональные критерии

| Требование | Критерий |
|---|---|
| API < 200 мс | Соответствие согласованной метрике и условиям измерения |
| 10 000 одновременных пользователей | Устойчивая работа по согласованной нагрузочной модели |
| SLA 99,9% | Соответствие утверждённой формуле за установленный период |
| Плановый простой ≤ 8 часов в год | Соблюдение отдельного ограничения по утверждённым правилам |
| Auto-scaling | Соответствие согласованным условиям масштабирования |
| DRM | Соблюдение утверждённой модели цифровых прав |
| AI-рекомендации | Соответствие согласованным метрикам качества |
| BI | Соответствие контрольным расчётам и метрикам |
| Безопасность | Отсутствие неприемлемых уязвимостей и выполнение применимых проверок соответствия |

**[В]** Численные пороги и методики, отсутствующие в паспорте, должны быть согласованы до окончательной оценки.

### 7.6. Порядок принятия решения

**[П]** Предлагаются:

- **Go** — обязательные критерии выполнены.
- **Conditional Go** — присутствуют документально принятые остаточные риски, не нарушающие обязательные критерии.
- **No-Go** — обязательные критерии не выполнены.

Условия применения Conditional Go должны утверждаться отдельно.

### 7.7. Незавершённые и неопределённые требования

Если требование входит в согласованный состав релиза, но критерий не определён, его нельзя считать успешно проверенным.

Возможные действия:

1. Получить уточнение.
2. Утвердить проверяемый критерий.
3. Выполнить тест.
4. Либо документально изменить состав релиза.

## 8. Критерии приостановки и возобновления (Suspension Criteria and Resumption Requirements)

### 8.1. Основания приостановки

**[П]** Тестирование приостанавливается полностью или в затронутой части при:

1. Недоступности критической среды.
2. Блокирующем дефекте.
3. Риске повреждения данных.
4. Неконтролируемой конфигурации.
5. Отсутствии необходимого интеграционного сервиса.
6. Критической проблеме безопасности.
7. Несоответствии переданной сборки заявленной версии.
8. Отсутствии обязательных тестовых данных.
9. Отсутствии достоверного ожидаемого результата.
10. Риске недопустимого воздействия нагрузочного теста на инфраструктуру.

### 8.2. Ответственность за остановку

**[П]** QA Lead принимает решение о приостановке тестовых работ в пределах предоставленных полномочий.

Для ситуаций, связанных с безопасностью или инфраструктурой, решение согласуется с ответственными специалистами.

**[В]** Окончательные полномочия должны быть утверждены проектом.

### 8.3. Возобновление

Для продолжения необходимо:

- устранить причину остановки;
- проверить работоспособность;
- зафиксировать конфигурацию;
- восстановить данные;
- повторить затронутые тесты;
- выполнить необходимую регрессию;
- зарегистрировать решение.

### 8.4. Учёт результатов

Прерванные тесты получают статус Blocked, если не установлено отклонение самого продукта.

После возобновления они выполняются повторно.

Результаты, полученные на неисправной или неопределённой конфигурации, не используются для окончательной приёмки без подтверждения их достоверности.

## 10. Задачи тестирования (Test Tasks)

### 10.1. Анализ требований

Задачи:

1. Изучить паспорт.
2. Выявить неоднозначности.
3. Подготовить реестр вопросов.
4. Назначить идентификаторы требованиям.
5. Определить приоритеты риска.
6. Подготовить предварительную матрицу покрытия.

Результат: контролируемый реестр требований и открытых вопросов.

### 10.2. Планирование

Задачи:

1. Уточнить состав Full Version.
2. Определить стратегию.
3. Согласовать уровни тестирования.
4. Назначить ответственных.
5. Оценить трудоёмкость.
6. Определить среды.
7. Согласовать критерии.

Результат: утверждённая применимая редакция тест-плана.

### 10.3. Проектирование тестов

Задачи:

- проектирование функциональных тестов;
- проектирование негативных проверок;
- граничные проверки;
- матрица ролей;
- интеграционные контракты;
- сквозные сценарии;
- нагрузочная модель;
- проверки безопасности;
- тестовые данные.

Результат: спецификации тест-кейсов и процедур.

### 10.4. Подготовка среды

Задачи:

- развёртывание;
- настройка БД;
- настройка провайдеров;
- подготовка пользователей;
- загрузка данных;
- настройка мониторинга;
- настройка логирования;
- проверка доступности компонентов.

Результат: зарегистрированная работоспособная тестовая конфигурация.

### 10.5. Выполнение

Предлагаемый порядок:

1. Smoke-тестирование.
2. Компонентные проверки.
3. Интеграционные проверки.
4. Функциональное системное тестирование.
5. Сквозное тестирование.
6. Нефункциональные испытания.
7. Регрессионное тестирование.
8. Приёмочное тестирование.

Независимые работы могут выполняться параллельно.

### 10.6. Управление дефектами

Задачи:

1. Зарегистрировать отклонение.
2. Указать сборку и среду.
3. Описать воспроизведение.
4. Определить серьёзность.
5. Передать исполнителю.
6. Проверить исправление.
7. Выполнить необходимую регрессию.
8. Закрыть дефект либо зафиксировать решение по остаточному риску.

### 10.7. Отчётность

По завершении тестового цикла формируются:

- отчёт о покрытии;
- результаты тестов;
- перечень дефектов;
- результаты нефункциональных испытаний;
- ограничения;
- остаточные риски;
- рекомендация о готовности.

| Задача | Необходимое условие |
|---|---|
| Проектирование тестов | Проверяемые требования |
| Автоматизация | Достаточно стабильный интерфейс или контракт |
| Интеграционное тестирование | Контракты и доступные компоненты |
| Системное тестирование | Развёрнутая работоспособная сборка |
| Нагрузочное тестирование | Репрезентативная среда и модель |
| Проверка безопасности | Определённая конфигурация и границы |
| Приёмочное тестирование | Утверждённые критерии |

**Изменение требований:** пересмотреть покрытие, трудоёмкость, риски и критерии.

**Недостаток персонала:** оценить перераспределение, обучение и дополнительное привлечение специалистов.

**Неготовая функция:** определить соответствие согласованному составу Full Version. Исключение возможно только через контролируемое изменение.
